# D6 — динамическое окно контекста перевода

| | |
| :-- | :-- |
| Файл | `app/translation/context.py` |
| Уровень | Middle |
| Оценка | 130 LOC, 8 тестов |
| Зависит от | `app/db.py` (готов), D1 (`base.py`) |
| Блокирует | обработчик `JobType.TRANSLATE`, качество перевода коротких реплик |
| Пункт спеки | §10 «Контекст перевода», §19 (`[translation.context]`) |

## Задача

Собрать окно предыдущих реплик того же потока для подстановки в запрос
перевода. Размер окна зависит от длины **текущего** сегмента: короткая
реплика без контекста переводится наугад («да», «сколько?»), длинная
самодостаточна, и лишний контекст только увеличивает счёт и задержку.

| Длина `raw_text` текущего сегмента, знаков | Окно |
| :-- | --: |
| < 100 | 4 |
| 100–200 включительно | 3 |
| > 200 | 2 |

Пороги и размеры — из конфига (`ContextConfig`), не из литералов.

## Интерфейс

```python
@dataclass(frozen=True, slots=True)
class ContextConfig:
    window_short: int = 4
    window_mid: int = 3
    window_long: int = 2
    short_chars: int = 100
    long_chars: int = 200

def window_for(length: int, cfg: ContextConfig) -> int: ...

async def build_context(db: Database, segment_id: str,
                        cfg: ContextConfig) -> tuple[str, ...]: ...
```

## Поведение

1. **Один запрос к БД на вызов.** Сначала читается текущий сегмент
   (`raw_text`, `stream_id`, `t_start_ms`), затем одним `SELECT` —
   предшествующие. Никаких `N+1` и никаких обходов в Python по всей
   таблице: функция работает в горячем пути каждого сегмента.

2. **Фильтры выборки — все обязательны:**
   - тот же `stream_id` (не `session_id`: реплики собеседника не являются
     контекстом ваших реплик и наоборот);
   - `track = 'accurate'` — результаты быстрого трека в контекст не
     попадают никогда (инвариант спеки §8.3);
   - `t_start_ms < t_start_ms` текущего сегмента, строго;
   - `raw_text` непустой после `trim`;
   - сам текущий сегмент исключён.

3. **Порядок.** Выборка идёт `ORDER BY t_start_ms DESC LIMIT n`,
   результат **разворачивается** в хронологический порядок перед возвратом.
   Обратный порядок в промпте читается моделью как обратный ход диалога и
   ломает разрешение местоимений.

4. **Возвращается `raw_text`, не перевод.** Контекст даётся на языке
   оригинала: модель переводит текущий сегмент, опираясь на исходные
   реплики. Подстановка `translation_raw` дала бы модели её же предыдущий
   вывод и закрепляла бы ошибки перевода.

5. **Границы окна.** `window_for`: `length < short_chars` → `window_short`;
   `short_chars <= length <= long_chars` → `window_mid`; иначе
   `window_long`. Длина считается по `raw_text` текущего сегмента в
   символах, не в байтах и не в токенах.

6. **Профиль не фильтрует контекст.** `TEXT_TO_CLOUD` разрешён в обоих
   профилях (`CAPABILITY_MATRIX`), поэтому отбрасывать сегменты с
   `privacy_profile='confidential'` не нужно. Право на сетевой вызов
   проверяет провайдер, не этот модуль.

7. **Отсутствие сегмента** с указанным `segment_id` → `InvariantViolation`
   с кодом `segment_not_found`. Это дефект вызывающего кода, а не штатная
   ситуация: задача перевода ставится после записи сегмента.

8. **Нехватка предыстории — норма.** В начале сессии предшественников нет
   или их меньше окна: возвращается кортеж меньшей длины, вплоть до
   пустого. Исключения нет.

9. **Функция без записи.** Только чтение через `db.fetch_one` /
   `db.fetch_all`. Ни `db.write`, ни постановки задач.

## Запрещено

- Брать контекст из другого `stream_id` или другой сессии.
- Включать сегменты быстрого трека (`track='fast'`) и вытесненные
  (`superseded_by_segment_id IS NOT NULL` относится только к fast, но
  фильтр по `track` обязателен явно).
- Подставлять `translation_raw` вместо `raw_text`.
- Возвращать контекст в обратном хронологическом порядке.
- Хардкодить 4/3/2 и пороги 100/200 — только из `ContextConfig`.
- Обрезать или модифицировать `raw_text`: он неизменяем (§8.1), в контекст
  идёт как есть, обрезается только окружающий пробел.
- Кэшировать результат между сегментами: список предшественников меняется
  по мере дозаписи точного трека.

## Критерии приёмки

- [ ] `window_for(50, cfg) == 4`, `window_for(100, cfg) == 3`,
      `window_for(200, cfg) == 3`, `window_for(201, cfg) == 2`
- [ ] Сегмент 50 знаков при 6 предшественниках → ровно 4 элемента
- [ ] Сегмент 300 знаков при 6 предшественниках → ровно 2 элемента
- [ ] Порядок элементов — хронологический (первый элемент самый ранний)
- [ ] Сегменты другого `stream_id` в выдачу не попадают
- [ ] Сегменты `track='fast'` в выдачу не попадают
- [ ] Сегмент с `raw_text=''` пропущен, окно добирается следующим
- [ ] Первый сегмент сессии → `()` без исключения
- [ ] Несуществующий `segment_id` → `InvariantViolation`
- [ ] Пороги из нестандартного `ContextConfig` (например 5/2/1, 80/150)
      соблюдаются
- [ ] Функция не выполняет ни одной операции записи (проверяется
      подменённым `Database` с падающим `write`)

## Подсказки

Запрос предшественников:

```sql
SELECT raw_text
FROM segments
WHERE stream_id = ?
  AND track = 'accurate'
  AND t_start_ms < ?
  AND raw_text IS NOT NULL
  AND TRIM(raw_text) <> ''
ORDER BY t_start_ms DESC
LIMIT ?
```

Индекс `(stream_id, track, t_start_ms)` обязателен — без него запрос
превращается в скан таблицы к середине часовой сессии. Если его нет в
миграциях, добавить миграцию отдельным пунктом и указать это в PR.

Ловушки:
- `t_start_ms` может совпадать у двух сегментов при склейке потоков —
  добавить вторичную сортировку по `id`, иначе порядок недетерминирован
  и тест начнёт мигать;
- длина считается по текущему сегменту, а не по предыдущему и не по сумме
  контекста — типичная ошибка при чтении спеки по диагонали;
- на очень коротких репликах («да») окно 4 может дать контекст длиннее
  переводимого текста — это ожидаемо и правильно, урезать не надо.
