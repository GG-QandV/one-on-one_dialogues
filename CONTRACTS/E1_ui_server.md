## Задача

Односторонний канал «сервер → браузер» для живого обновления интерфейса и
минимальный HTTP-слой поверх него.

Выбран SSE, а не WebSocket, по существу задачи: поток событий идёт в одну
сторону, команды пользователя (старт, стоп, переключение профиля) —
обычные POST-запросы. SSE переживает разрыв соединения штатными
средствами браузера и не требует своего протокола переподключения.

Адрес по спеке §14: `http://127.0.0.1:8790`. Наружу не слушать никогда:
в потоке событий идут расшифровки переговоров.

## Интерфейс

```python
@dataclass(frozen=True, slots=True)
class UiConfig:
    host: str = "127.0.0.1"
    port: int = 8790
    heartbeat_s: float = 15.0
    queue_max: int = 500          # событий на клиента

class EventType(str, Enum):
    SEGMENT_PARTIAL = "segment.partial"
    SEGMENT_FINAL = "segment.final"
    SEGMENT_TRANSLATED = "segment.translated"
    DRAFT_CREATED = "draft.created"
    DRAFT_TRANSLATED = "draft.translated"
    PRIVACY_CHANGED = "privacy.changed"
    STATUS = "status"

@dataclass(frozen=True, slots=True)
class UiEvent:
    type: EventType
    data: dict[str, Any]
    sequence: int                 # монотонный, общий для всех типов

class UiServer:
    def __init__(self, app: Application, config: UiConfig | None = None): ...
    async def start(self) -> None
    async def stop(self) -> None
    def publish(self, type: EventType, data: dict) -> None   # неблокирующий
    def snapshot(self) -> dict
```

## Поведение

1. **Формат событий фиксирован `INTERFACES.md` §7.1 и менять его нельзя** —
   клиент E2 пишется против него:

   | Событие | Payload |
   | :-- | :-- |
   | `segment.partial` | `{utterance_id, role, text, t_start_ms, track:"fast"}` |
   | `segment.final` | `{segment_id, role, raw_text, t_start_ms, t_end_ms, track:"accurate"}` |
   | `segment.translated` | `{segment_id, translation, mode, superseded_ids[]}` |
   | `draft.created` | `{draft_id, trigger_segment_id, draft_ru, sources[], has_gaps}` |
   | `draft.translated` | `{draft_id, draft_translated}` |
   | `privacy.changed` | `{profile, generation, teardown_ms}` |
   | `status` | `{state, degradation_level, backlog_ms, latency_ms}` |

   Проводной формат: `event: {type}\ndata: {json}\nid: {sequence}\n\n`.

2. **`sequence` монотонный и сквозной** для всех типов событий, начинается
   с 1 при старте сервера. Он же уходит в поле `id:` SSE. Клиент строит
   на нём дедупликацию (E2), поэтому пропуски и повторы номеров
   недопустимы.

3. **`publish` не блокирует и не бросает.** Вызывается из конвейера
   обработки, где задержка стоит миллисекунд бюджета. Событие кладётся в
   очередь каждого подключённого клиента; очередь полна → **отбрасывается
   самое старое** событие этого клиента, счётчик потерь растёт.
   Останавливать конвейер из-за медленного браузера нельзя.

4. **Снапшот вместо переигрывания истории.** При подключении клиент
   получает `GET /api/snapshot` — текущее состояние (последние N
   сегментов, активные черновики, профиль, статус). История событий на
   сервере не хранится и при reconnect не переигрывается: `Last-Event-ID`
   принимается, но используется только для отсечения дублей на клиенте.

5. **Heartbeat** — комментарий SSE (`: ping\n\n`) каждые `heartbeat_s`.
   Без него прокси и браузер закрывают простаивающее соединение, а в
   тихой встрече событий может не быть минутами.

6. **Обязательные HTTP-эндпоинты:**

   | Метод и путь | Назначение |
   | :-- | :-- |
   | `GET /events` | Поток SSE |
   | `GET /api/snapshot` | Состояние для первичной отрисовки |
   | `POST /api/session/start`, `/stop` | Управление сессией |
   | `POST /api/privacy` | Переключение профиля |
   | `GET /health`, `GET /ready` | Спека §17 |

   `/health` отвечает всегда при живом процессе; `/ready` — только когда
   БД открыта, очередь запущена и STT инициализирован.

7. **Привязка только к `127.0.0.1`.** Значение из конфига, но любое
   значение, кроме петлевого адреса, при старте даёт предупреждение
   уровня WARNING с явной формулировкой риска. Авторизации в MVP нет —
   она и не нужна на петле, но именно поэтому выход наружу должен быть
   заметным.

8. **Профиль конфиденциальности не ограничивает UI.** Локальный интерфейс
   показывает всё: ограничение профиля — про отправку в облако, не про
   экран пользователя.

9. **Множественные клиенты.** Две вкладки браузера — штатная ситуация,
   каждая получает свою очередь. Ограничение на число подключений не
   вводится; счётчик — в `snapshot()`.

10. **Корректное завершение.** `stop()` закрывает все потоки, дожидается
    отправки буферов не дольше секунды и не мешает порядку остановки
    приложения (UI останавливается первым, `INTERFACES.md` §8).

## Запрещено

- Менять имена событий и состав полей из §7.1 без правки `INTERFACES.md`.
- Блокировать `publish` ожиданием клиента.
- Хранить историю событий на сервере ради переигрывания при reconnect.
- Слушать `0.0.0.0` молча.
- Добавлять WebSocket «на всякий случай»: два канала — два протокола
  синхронизации и два источника рассинхрона.
- Отдавать в событиях содержимое библиотеки фактов и ключи.
- Логировать payload событий на уровне INFO и выше: там расшифровка
  переговоров.
- Выполнять бизнес-логику в обработчиках: сервер транслирует вызовы в
  `Application` (готов) и ничего не решает сам.

## Критерии приёмки

- [ ] Событие приходит в формате `event:`/`data:`/`id:` с корректным JSON
- [ ] `sequence` монотонно растёт и совпадает с полем `id:`
- [ ] Два подключённых клиента получают одинаковую последовательность
- [ ] Переполнение очереди клиента: старые события отбрасываются, новые
      доставляются, счётчик потерь в `snapshot()` растёт, `publish` не
      бросает
- [ ] `publish` из синхронного контекста конвейера не блокирует дольше
      единиц миллисекунд (тест с замером)
- [ ] Heartbeat приходит при отсутствии событий
- [ ] `GET /api/snapshot` возвращает состояние, достаточное для отрисовки
      без единого события
- [ ] `/health` отвечает 200 сразу после старта; `/ready` — только после
      инициализации зависимостей
- [ ] Хост, отличный от петлевого, даёт WARNING при старте
- [ ] Обрыв соединения клиента не приводит к исключению в конвейере
- [ ] `stop()` закрывает все соединения; повторный вызов безопасен
- [ ] Payload событий отсутствует в логах уровня INFO и выше

## Подсказки

Каркас потока:

```python
async def events(request):
    queue: asyncio.Queue[UiEvent] = asyncio.Queue(maxsize=cfg.queue_max)
    self._clients.add(queue)
    try:
        while True:
            try:
                ev = await asyncio.wait_for(queue.get(), cfg.heartbeat_s)
                yield f"event: {ev.type.value}\ndata: {json.dumps(ev.data, ensure_ascii=False)}\nid: {ev.sequence}\n\n"
            except asyncio.TimeoutError:
                yield ": ping\n\n"
    finally:
        self._clients.discard(queue)
```

Ловушки:
- `ensure_ascii=False` обязателен: иначе весь русский и испанский текст
  уходит в `\uXXXX` и раздувает трафик втрое;
- перевод строки внутри `data:` разрывает событие — многострочный текст
  экранируется самим `json.dumps`, но собственная конкатенация строк
  этого не сделает;
- заголовки ответа: `Content-Type: text/event-stream`,
  `Cache-Control: no-cache`, `X-Accel-Buffering: no` — без последнего
  события копятся в буфере при работе через прокси;
- `finally` с `discard` обязателен: без него закрытые вкладки накапливают
  мёртвые очереди, и `publish` начинает тратить время на них;
- статические файлы UI отдаются этим же сервером — путь к ним из
  конфига, не относительно `__file__`.
