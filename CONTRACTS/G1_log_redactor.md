# G1 — маскирование секретов в логах

| | |
| :-- | :-- |
| Файл | `app/security/redactor.py` |
| Уровень | Middle |
| Оценка | 190 LOC, 12 тестов |
| Зависит от | `app/errors.py` (готов) |
| Блокирует | **G2 (BYOK) — порядок жёсткий**, любые живые тесты с ключом |
| Пункт спеки | §16 (`LogRedactor`) |

## Задача

Фильтр логирования, который вырезает ключи провайдеров из всего, что
уходит в лог, — включая трейсы исключений.

**Порядок работ жёсткий: G1 полностью готов и подключён до начала G2.**
Иначе первый же живой тест с настоящим ключом запишет его в файл лога, и
дальше ключ придётся отзывать у провайдера, а лог — искать и чистить.

Спека §16 запрещает попадание ключа в SQLite, файлы, URL, cookies,
аналитику, **exception traces**, access- и debug-логи. Трейсы названы
отдельно не случайно: `httpx` кладёт заголовки запроса в текст исключения
при ошибках соединения, и стандартный `logging.Filter`, правящий только
`record.msg`, их не покрывает.

## Интерфейс

```python
DEFAULT_PATTERNS: tuple[str, ...]      # известные формы ключей провайдеров
MASK = "***REDACTED***"

class LogRedactor(logging.Filter):
    def __init__(self, patterns: Iterable[str] | None = None,
                 *, mask: str = MASK) -> None: ...
    def add_pattern(self, regex: str) -> None: ...
    def add_literal(self, secret: str) -> None: ...   # точное значение ключа
    def remove_literal(self, secret: str) -> None: ...
    def redact(self, text: str) -> str: ...
    def filter(self, record: logging.LogRecord) -> bool: ...   # всегда True
    def snapshot(self) -> dict: ...    # число паттернов и срабатываний,
                                       # без самих секретов
```

## Поведение

1. **Правятся четыре поля записи, не одно:**
   - `record.msg` — шаблон сообщения;
   - `record.args` — подставляемые значения (кортеж или словарь,
     обрабатывать оба варианта);
   - `record.exc_text` — уже отформатированный трейс, если он есть;
   - `record.exc_info` — трейс, ещё не отформатированный: его нужно
     привести к тексту, замаскировать и положить в `exc_text`, обнулив
     `exc_info`, иначе форматтер соберёт трейс заново из объекта
     исключения и обойдёт фильтр.

   Пропуск последнего пункта — самая частая и самая дорогая ошибка в этом
   модуле: сообщение чистое, трейс с ключом.

2. **`filter` всегда возвращает `True`.** Задача — вычистить запись, а не
   подавить её. Подавленный лог в момент инцидента с провайдером стоит
   дороже, чем замаскированное сообщение.

3. **Два вида правил:**
   - **паттерны** — регулярные выражения известных форм ключей
     (`sk-…`, `AIza…`, `Bearer …`), работают до того, как конкретный ключ
     станет известен;
   - **литералы** — точное значение действующего ключа, добавляется
     `KeyStore` (G2) при вводе и снимается при `revoke`. Литерал
     страхует от нестандартной формы ключа, которую не покрыл паттерн.

4. **Литералы не хранятся в открытом виде дольше необходимого.** Внутри
   хранится сам литерал (иначе маскировать нечем), но он **не попадает**
   в `snapshot()`, в `repr` объекта и в сообщения исключений. Объект
   `LogRedactor` не сериализуется.

5. **Маскируется значение, а не строка целиком.** `x-api-key: sk-abc123`
   → `x-api-key: ***REDACTED***`. Полное затирание сообщения лишает лог
   диагностической ценности — а он нужен ровно для разбора инцидентов.

6. **Частичное совпадение тоже маскируется.** Ключ, разорванный
   переносом строки в трейсе, встречается регулярно. Правило: литерал
   ищется как есть; дополнительно ищется его версия с удалёнными
   пробельными символами по нормализованной копии текста, и при
   совпадении маскируется соответствующий фрагмент оригинала.

7. **Производительность.** Регулярные выражения компилируются один раз
   при добавлении. Фильтр вызывается на каждой записи лога; поиск по
   десятку скомпилированных паттернов допустим, пересборка `re.compile`
   на каждой записи — нет.

8. **Подключение — ко всем логгерам до первого логирующего вызова.**
   Место подключения — `app/logging_setup.py` (E1/F-блок), первым
   действием `Application.start()`. Фильтр вешается на **обработчики**
   (`Handler`), а не только на корневой логгер: фильтры логгера не
   применяются к записям, пришедшим от дочерних логгеров через
   propagation.

9. **Идемпотентность.** Повторное добавление того же паттерна или
   литерала дубликата не создаёт. `redact` на тексте без секретов
   возвращает тот же объект строки без изменений.

## Запрещено

- Возвращать `False` из `filter` (подавлять записи).
- Класть секреты в `snapshot()`, `repr`, `str` и в исключения модуля.
- Логировать факт срабатывания вместе с замаскированным фрагментом
  («замаскировано: sk-abc…») — это тот же ключ, только с префиксом.
- Компилировать регулярные выражения внутри `filter`.
- Подключать фильтр только к корневому логгеру.
- Полагаться на то, что провайдеры не кладут ключ в исключения:
  правило «исключения свободны от секретов» (`SecretFreeError`) —
  наш код, а `httpx`, `asyncio` и стандартная библиотека ему не следуют.
- Начинать G2 до полного прохождения приёмки этого контракта.

## Критерии приёмки

- [ ] `sk-CANARY-12345` в `record.msg` замаскирован
- [ ] Ключ в `record.args` (кортеж) замаскирован
- [ ] Ключ в `record.args` (словарь, `%(key)s`-форматирование)
      замаскирован
- [ ] Ключ в `record.exc_text` замаскирован
- [ ] Ключ внутри `exc_info` (трейс ещё не отформатирован) замаскирован;
      после фильтра `exc_info is None`, `exc_text` заполнен
- [ ] Вложенное исключение (`raise … from …`, цепочка `__cause__`)
      маскируется целиком
- [ ] Ключ, разорванный переносом строки, замаскирован
- [ ] Форматы `sk-…`, `AIza…`, `Bearer …` покрываются паттернами по
      умолчанию, без добавления литерала
- [ ] `add_literal` + `remove_literal`: после удаления литерала форма,
      не покрытая паттернами, больше не маскируется (проверка отзыва)
- [ ] `filter` возвращает `True` во всех случаях
- [ ] Сообщение без секретов не изменяется
- [ ] `snapshot()` не содержит ни литералов, ни фрагментов ключей
- [ ] Интеграционный тест: логгер с фильтром на обработчике, запись через
      дочерний логгер `app.translation.providers.gemini_text` — ключ в
      файле лога отсутствует (грепом по файлу)

## Подсказки

Паттерны по умолчанию (список расширяется по мере подключения
провайдеров, значения — примерные формы, не полные спецификации):

```python
DEFAULT_PATTERNS = (
    r"sk-[A-Za-z0-9_\-]{16,}",           # OpenAI, Anthropic
    r"AIza[A-Za-z0-9_\-]{20,}",          # Google
    r"(?i)bearer\s+[A-Za-z0-9._\-]{16,}",
    r"(?i)(x-api-key|x-goog-api-key|authorization)\s*[:=]\s*\S+",
)
```

Обработка `exc_info` — ключевой фрагмент:

```python
if record.exc_info:
    record.exc_text = self.redact(
        "".join(traceback.format_exception(*record.exc_info)))
    record.exc_info = None
```

Ловушки:
- `record.getMessage()` вызывать для проверки можно, но правку делать
  нужно в `msg` и `args` раздельно — иначе теряется отложенное
  форматирование и падают обработчики, ожидающие `args`;
- `record.args` может быть словарём (при `%(name)s`-стиле) — проверять
  тип, а не считать кортежем;
- последний паттерн из списка перекрывает случай, когда ключ имеет
  нестандартную форму, но передан в заголовке — это дешёвая страховка,
  снимать её не надо;
- жадные квантификаторы в паттернах вида `.*` затирают полстроки лога;
  ограничивать класс символов явно;
- тест «ключ не в файле» пишется на реальный `FileHandler` во временной
  директории: проверка на in-memory обработчике не поймает ошибку
  подключения фильтра к обработчику.
