# F1 — поставщик метрик памяти

| | |
| :-- | :-- |
| Файл | `app/watchdog/memory.py` |
| Уровень | Middle+ |
| Оценка | 230 LOC, 12 тестов |
| Зависит от | `app/watchdog/degradation.py` (F2, готов) |
| Блокирует | F2 (каскад деградации), E6 (диагностический экран) |
| Пункт спеки | §15, §19 (`[memory]`) |

## Задача

Мерить фактическое потребление памяти процессом и его дочерними
процессами, вести короткую историю и отдавать её каскаду деградации (F2,
реализован) и диагностическому экрану.

Бюджет по спеке §15: расчётный потолок 1350–1840 МБ, `MemoryHigh=1750M`,
`MemoryMax=2000M`, опрос каждые 2 секунды. Пороги каскада — 1750 МБ
(не брать новые задачи) и 1900 МБ (остановить STT, режим только записи).

Главная ловушка модуля названа прямо в `INTERFACES.md` §6.2: **whisper.cpp
запускается отдельным процессом**, и его 550–700 МБ не видны в `VmRSS`
Python-процесса. Модуль, который меряет только себя, покажет 300 МБ в тот
момент, когда система упирается в лимит cgroup.

## Интерфейс

```python
@dataclass(frozen=True, slots=True)
class MemoryConfig:
    interval_s: float = 2.0
    history_size: int = 300            # 10 минут при интервале 2 с
    high_mb: float = 1750.0
    max_mb: float = 1900.0

@dataclass(frozen=True, slots=True)
class MemorySample:
    at_ms: int
    total_mb: float
    self_mb: float
    children_mb: float
    source: Literal["cgroup", "vmrss"]

class MemoryMonitor:
    def __init__(self, config: MemoryConfig | None = None,
                 *, clock: Callable[[], float] = time.monotonic) -> None: ...
    async def start(self) -> None
    async def stop(self) -> None
    def read(self) -> MemorySample          # синхронное разовое измерение
    def current_mb(self) -> float           # интерфейс MemoryReader для F2
    source: str                             # "cgroup" | "vmrss"
    def history(self, n: int | None = None) -> tuple[MemorySample, ...]
    def peak_mb(self) -> float
    def snapshot(self) -> dict
```

## Поведение

1. **Источник выбирается один раз при старте, приоритет жёсткий:**
   1. cgroup v2: `/sys/fs/cgroup/memory.current` (файл процесса, путь
      берётся из `/proc/self/cgroup`);
   2. cgroup v1: `/sys/fs/cgroup/memory/memory.usage_in_bytes`;
   3. `VmRSS` из `/proc/self/status` + сумма `VmRSS` дочерних процессов.

   Выбранный источник фиксируется в поле `source` и уходит в `snapshot()`.

2. **Режим `vmrss` — деградировавший, и это должно быть видно.** При
   `source == "vmrss"` монитор обязан:
   - явно предупредить в лог **один раз** при старте (уровень WARNING);
   - выставить флаг `degraded_source: true` в `snapshot()` для экрана E6;
   - суммировать дочерние процессы (см. п. 3), а не мерить только себя.

3. **Дочерние процессы.** Обход `/proc/{pid}/task/*/children` либо
   перечисление `/proc/*/status` с фильтром по `PPid`. Учитываются
   рекурсивно: whisper.cpp может быть запущен через обёртку. Недоступный
   или исчезнувший процесс пропускается молча — гонка с завершением
   процесса нормальна и не является ошибкой.

4. **`current_mb` — это контракт `MemoryReader` из F2 (готов).** Сигнатура
   и семантика менять нельзя: каскад уже написан против неё. `current_mb`
   возвращает последнее измеренное значение, не выполняет чтение с диска
   и не блокирует — вызывается из тика каскада.

5. **Опрос неблокирующий.** Чтение `/proc` и cgroup — синхронный
   файловый ввод-вывод; он короткий, но выполняется в
   `run_in_executor` при обходе дочерних процессов (их может быть
   десяток). Правило `INTERFACES.md` §0 про блокирующие вызовы
   действует.

6. **История — кольцевой буфер** на `history_size` элементов. Отдаётся
   копией: наружу уходит `tuple`, внутренняя структура не мутируется
   потребителем. Это данные для графика на E6, а не для решений.

7. **Решений о деградации модуль не принимает.** Пороги `high_mb` и
   `max_mb` он знает только чтобы отдать в `snapshot()` расстояние до
   них. Действия (`pause_cloud_jobs`, `stop_stt`) — исключительно
   `DegradationCascade` (F2).

8. **Устойчивость к отсутствию файлов.** Любая ошибка чтения источника →
   переход на следующий по приоритету, а не исключение. Полная
   недоступность всех источников → `current_mb()` возвращает `0.0`,
   `snapshot()` содержит `available: false`. Каскад в этом случае обязан
   продолжать работать по остальным сигналам, а не падать.

9. **`peak_mb`** — максимум за время жизни монитора, не за окно истории.
   Сбрасывается только `stop()` + `start()`.

10. **Часы инжектируются** параметром `clock` — тесты интервалов не
    должны спать.

## Запрещено

- Мерить только собственный процесс при `source == "vmrss"`: главный
  потребитель памяти — дочерний whisper.
- Скрывать факт работы через `vmrss`: без предупреждения деградировавший
  источник выглядит как исправный и врёт в меньшую сторону.
- Принимать решения о деградации, останавливать STT, ставить задачи на
  паузу.
- Тянуть `psutil` и другие внешние зависимости: `/proc` и cgroup читаются
  штатными средствами, лишняя зависимость в MVP не нужна.
- Бросать исключения из `current_mb()` — он вызывается из тика каскада,
  и падение там останавливает всю защиту от OOM.
- Хардкодить 1750/1900: пороги из `[memory]` конфига.
- Логировать каждое измерение: 0.5 записи в секунду × час встречи —
  мусор в логах и лишний ввод-вывод. Лог только при пересечении порога.

## Критерии приёмки

- [ ] При доступном cgroup v2 `source == "cgroup"`, значение совпадает с
      содержимым подменённого `memory.current` (± округление)
- [ ] Недоступный cgroup v2 → переход на v1, затем на `vmrss`
- [ ] `source == "vmrss"` → предупреждение в логе ровно один раз за
      время жизни монитора, `degraded_source: true` в `snapshot()`
- [ ] В режиме `vmrss` память дочернего процесса входит в `total_mb`
      (проверяется подменённым деревом `/proc`)
- [ ] Исчезнувший дочерний процесс между обходом и чтением не приводит к
      исключению
- [ ] `current_mb()` не выполняет файлового ввода-вывода (проверяется
      подменённым `open`, который падает)
- [ ] Все источники недоступны → `current_mb() == 0.0`,
      `snapshot()["available"] is False`, исключения нет
- [ ] История ограничена `history_size`, старые элементы вытесняются
- [ ] `history()` возвращает копию: мутация результата не влияет на
      внутреннее состояние
- [ ] `peak_mb` сохраняется после падения текущего значения
- [ ] `MemoryMonitor` подставляется в `DegradationCascade` как
      `memory_reader` без адаптера (интеграционный тест с F2)
- [ ] `stop()` останавливает опрос; повторный вызов безопасен

## Подсказки

Определение пути cgroup v2 для собственного процесса:

```python
# /proc/self/cgroup в v2 содержит одну строку вида "0::/user.slice/..."
line = Path("/proc/self/cgroup").read_text().strip()
rel = line.split("::", 1)[1]
path = Path("/sys/fs/cgroup") / rel.lstrip("/") / "memory.current"
```

Значения в cgroup — байты, в `/proc/*/status` — килобайты. Смешение
единиц даёт ошибку в 1024 раза и порог, который никогда не сработает;
конверсию делать в одном месте.

Ловушки:
- `memory.current` в cgroup включает page cache, поэтому значение выше
  «честного» RSS и ближе к тому, по чему сработает OOM-killer — это
  правильный источник, занижать его вычитанием кэша не нужно;
- при запуске не под systemd (в тестах, в отладке) cgroup-файл
  существует, но относится к пользовательской сессии целиком и включает
  браузер — в диагностике E6 стоит показывать `source`, чтобы это было
  видно глазом;
- `[memory].high_mb = 1750` в конфиге и `MemoryHigh=1750M` в unit-файле —
  два независимых места; расхождение обнаружится только под нагрузкой,
  проверку соответствия стоит вынести в старт приложения.
