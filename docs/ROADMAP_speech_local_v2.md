# ROADMAP / WORKFLOW: speech-local v2.0

Используется наравне с `SPEC_speech_local_v2.md`.
Метрика планирования: **задачи, LOC, итерации ревью, вероятности** — не дни и не часы.
Версия 2.0 отменяет и заменяет v1.0.

---

## 0. Как читать документ

| Колонка | Смысл                                                          |
|:------- |:-------------------------------------------------------------- |
| ID      | Идентификатор задачи; используется в коммитах, ревью и отчётах |
| LOC     | Оценка объёма кода, разброс ±15% (достоверность 85%)           |
| Ур.     | Требуемый уровень исполнителя                                  |
| P1      | Вероятность прохождения обоих ревью с первого раза             |
| Итер.   | Ожидаемое число циклов «правка → ревью», ≈ 1/P1                |
| Тесты   | Количество тестов / ожидаемое число правок тестов              |

**Правило дробления:** задача с P1 ≤ 45% дробится Архитектором до передачи исполнителю.

**Достоверность прогнозов:** LOC — 85%; P1 — 60–70%; количество тестов — 75%; вероятности архитектурных срывов — 60–70%.

## 1. Роли и конвейер

### 1.1 Исполнители (только написание кода)

| Уровень    | Модели                    | Что берут                                                               |
|:---------- |:------------------------- |:----------------------------------------------------------------------- |
| Junior     | DeepSeek Flash, Haiku 4.5 | Изолированные модули с готовым контрактом и падающим тестом             |
| Middle     | DeepSeek Pro, Sonnet 4.6  | Модули с внешними зависимостями: HTTP, SSE, парсинг, провайдеры         |
| Senior     | Opus 4.8, Opus 5          | Сквозная логика, конкурентность, процессы, состояние, изоляция профилей |
| Архитектор | Opus 5, Fable 5           | Контракты, интерфейсы, каскад деградации, дробление задач               |

Модели-переводчики провайдеров (Gemini, Claude, OpenAI realtime) — **отдельная сущность**, к ролям исполнителей отношения не имеют. Финальный выбор провайдера — по живым тестам (задача H2).

### 1.2 Ревьюеры

| Ревьюер              | Зона                                                                                                            | Вето             |
|:-------------------- |:--------------------------------------------------------------------------------------------------------------- |:---------------- |
| **Владелец проекта** | Корректность архитектуры, соответствие функционала цели, качество выбора и настроек моделей, приёмка результата | Финальное        |
| **ChatGPT 5.6**      | Соответствие спеки архитектуре; соответствие кода спеке и архитектуре; выявление расхождений                    | На уровне задачи |
| Senior-агент         | Технический ревью кода Junior/Middle до внешнего ревью                                                          | Возвратное       |

### 1.3 Конвейер

```
Архитектор: контракт + падающий тест
  -> Исполнитель: реализация
  -> Senior-агент: технический ревью (для Junior/Middle)
  -> ChatGPT 5.6: соответствие спеке и архитектуре
  -> Владелец: архитектура, функционал, качество
  -> DONE либо возврат со ссылкой на пункт спеки
```

Возврат без ссылки на пункт спеки или контракта не принимается — это признак пробела в спеке, который сначала закрывается Архитектором.

| Событие                                        | Вероятность |
|:---------------------------------------------- | -----------:|
| Архитектура пройдёт реализацию без пересмотров | **15–20%**  |
| 1–2 существенных пересмотра                    | **50–55%**  |

## 16. Правила для агентов-исполнителей

1. **Задание = контракт + падающий тест.** Без обоих артефактов задача не берётся; возвращается запрос Архитектору.
2. **Запрет заглушек.** `pass`, `TODO`, `return None`, `assert True` в местах реальной логики — автоматический возврат по CI. Если реализовать невозможно — вернуть отказ с причиной, не имитацию.
3. **Запрет расширения области.** Правки вне файлов своей задачи запрещены; нужна правка чужого модуля — заявка Архитектору.
4. **Ссылка на спеку.** Каждое нетривиальное решение сопровождается ссылкой на пункт спеки. Решение без пункта — кандидат на пробел в спеке, эскалируется.
5. **Один контекст — одна задача.** Не помещается вместе с контрактом и тестом — возврат на дробление.
6. **Честный отчёт.** «Полностью выполнено» допустимо только при 100% прохождении контракт-тестов. При частичном — явный список невыполненного.
7. **Конфиг вместо хардкода.** Любая константа, влияющая на поведение, — в `config.toml`.
8. **Профиль конфиденциальности — сквозной инвариант.** Любой код, отправляющий данные наружу, обязан проверять текущий профиль. Отсутствие проверки — блокирующий дефект независимо от блока.

## 17. Что считается провалом этапа

- Отчёт о готовности при непройденных контракт-тестах.
- Обход инварианта неизменяемости `raw_text` или `privacy_profile`.
- Появление ключа BYOK в БД, файле, URL или логе.
- Отправка аудио наружу в конфиденциальном профиле.
- Попадание результатов быстрого трека в `raw_text` или экспорт.
- Черновик ответа, содержащий факт, отсутствующий в библиотеке, без пометки `has_gaps`.
- Любой путь доставки черновика без явного действия пользователя.
- Молчаливое изменение архитектурного решения исполнителем без эскалации.
- Тест, подогнанный под реализацию вместо реализации под контракт.
