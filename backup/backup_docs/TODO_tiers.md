## Tier 1.1 — Сменная библиотека фактов (I1)

**Цель:** библиотека (`app/drafts/library.py`, таблица `library_contexts`) заменяема под каждую сессию, не глобальна.

### Управление библиотеками (UI + backend)

- Пользователь создаёт несколько библиотек (тем/продуктов) через settings
- Активная библиотека выбирается перед стартом сессии (или переключается между сессиями)
- `[draft]` → `library_id` в `config.toml` или в `sessions.library_context_id` (уже есть в DDL)
- Кнопка «Утвердить» / «Сменить» / «Подгрузить» в topbar

### Валидация при смене

- Размер (token_estimate ≤ library_max_tokens — уже есть в `FactLibrary.check_limit`)
- Формат (структура данных, не пустой content_text)
- Проверка на занятость в другой сессии (уже есть в `delete()` → `sessions.library_context_id`)
- При превышении лимита — явная ошибка, не молчаливое усечение

### Backend

- `POST /api/library/{id}/select` — установить активную для следующей сессии
- `GET /api/library/active` — текущая выбранная
- Валидация при выборе, а не при старте сессии

## Tier 1.2 — Режим без перевода (транскрипция + саммари)

**Цель:** язык клиента == язык подсказок (en→en, ru→ru, uk→uk, pl→pl). Перевод отключён, работает STT + генерация черновиков + саммаризация + выводы.

### Что меняется

- `source_language == target_language` → `TranslationMode.PASSTHROUGH` или пропуск вызова провайдера перевода
- Сегменты записываются с `raw_text`, `translation_status = skipped`
- DraftProvider (`I2`) работает на том же языке (генерация не на ru, а на языке встречи)
- UI: вкладка «Перевод» показывает только оригинал, без поля перевода
- Q&A / саммари / выводы — новый тип черновиков (не ответ на вопрос, а резюме диалога)

### Новые сущности

- `DraftType`: `answer` (ответ на вопрос) / `summary` (саммари встречи) / `conclusion` (выводы)
- Триггеры: по паузе > N секунд / по команде / по завершению сессии
- Промпты: отдельные режимы `DRAFT_SUMMARY`, `DRAFT_CONCLUSION` в `prompts.py`

### UI

- Вкладка «Резюме» / «Выводы» рядом с «Черновики ответов»
- Авто-генерация при завершении сессии

## Tier 1.6 — Озвучка ответа собеседнику (live-интерпретация через gpt-realtime-translate)

**Зафиксировано:** 2026-07-29, обсуждение с владельцем. Не начинать без явного
запроса — требует пересмотра явного исключения TTS из спеки (см. ниже).

**Цель:** ваш ответ звучит собеседнику в звонке на его языке голосом, а не
читается им с экрана черновика.

**Важно — конфликтует с текущей спекой:** `SPEC_speech_local_v2.md`, раздел 14,
прямо помечает «TTS и озвучка — Исключено» (не Тир 2, а исключено насовсем).
Взятие этой задачи в работу требует ревью и правки спеки, а не только кода.

### Технический вариант (обсуждён, не единственный)

Модель [`gpt-realtime-translate`](https://developers.openai.com/api/docs/models/gpt-realtime-translate) —
потоковый speech-to-speech перевод одним вызовом (аудио-в → переведённое
аудио-вон + текстовый транскрипт), без отдельных STT/перевод/TTS шагов,
с адаптацией голоса под тон говорящего.

- **Только OPEN профиль.** Это `Capability.AUDIO_TO_CLOUD` — уже запрещено в
  CONFIDENTIAL текущей `CAPABILITY_MATRIX` (`app/privacy.py`), менять матрицу
  не нужно, ограничение уже есть.
- **Двусторонний режим = две сессии.** Документация прямо: «two-person call
  usually means two translation sessions: A-to-B and B-to-A». Ложится на уже
  существующие в схеме БД две записи `audio_streams` (role=`microphone`,
  role=`meeting`), по одной сессии на роль — переиспользовать паттерн
  `app/translation/providers/openai_realtime.py`, а не изобретать новый.
- Формат: 24кГц PCM16 на входе и выходе, чанки перевода по ~200мс.
- Цена — по длительности аудио, не по токенам (точные ставки не проверены).

### Что это НЕ решает

- **Инъекция звука в звонок.** Модель отдаёт PCM-чанки — донести их до
  Zoom/Meet/Teams как «микрофон» требует virtual-sink в PipeWire
  (свитчер: реальный микрофон ↔ синтезированный ответ), симметрично уже
  известной проблеме R5 (роадмап), но в обратную сторону. Отдельная задача
  класса C1 (аудио-модуль), не тривиальна.
- **Раскрытие собеседнику.** Не техническая, а продуктовая/юридическая
  развилка: собеседник слышит голос вместо вас без предупреждения, что это
  синтетический перевод. Решить ДО реализации, не после.

### Что это убирает (по сравнению с обычным TTS черновика)

- Не нужен отдельный `TTSProvider`/модуль синтеза — модель сама возвращает
  готовое аудио.
- Но также убирает ревью-чекпойнт: сейчас черновик недоставим без явного
  клика человека (`DraftGuard`, критерий приёмки H2 №11). Живая
  интерпретация — синхронная, без паузы на проверку, то есть теряется
  главная защита от риска R12 (генератор выдаёт факт вне библиотеки).
  Если брать в работу — обязательно спроектировать эквивалент чекпойнта
  (например, короткая буферизация с возможностью отменить произнесение),
  а не полагаться на то, что "модель сама разберётся".

### Отклонённая альтернатива

Публикация озвучки на отдельном сайте (Cloudflare Pages/Workers + R2),
собеседник открывает ссылку и слушает отдельно от звонка. Отклонено:
ломает живой диалог (асинхронная доставка вместо ответа в моменте) и
противоречит offline-first/local-only архитектуре и модели профиля
confidential (контент черновика оказывается на публичном URL).

## Tier 2 — Конфигурируемые локальные модели (STT/TTS/перевод) под конфиденциальность

**Зафиксировано:** 2026-07-29, обсуждение с владельцем. Не начинать без явного
запроса — требует пересмотра `SPEC_speech_local_v2.md` (два явных запрета,
см. ниже), а не только кода.

**Цель — не "локальность ради локальности", а закрытие второй утечки
конфиденциальности.** Текущий `confidential`-профиль (`CAPABILITY_MATRIX`,
`app/privacy.py`) контролирует только то, что *это приложение* отправляет
внешним AI-провайдерам (перевод, черновики). Он не может и не должен
пытаться контролировать то, что происходит с самим звонком —
Zoom/Meet/Teams получают голос/видео независимо от `speech-local`, просто
по факту звонка через них. Это две разные утечки, и первую можно закрыть
кодом этого репозитория, вторую — нет.

### Три независимых конфига + тестирование каждого

```toml
[stt]
mode = "local"          # local | cloud
model = "base"          # tiny|base|small|medium|large-v3|large-v3-turbo (+ q5/q8 кванты)

[tts]
mode = "local"          # local | cloud | off
model = "piper-ru-medium"

[translation]
mode = "local"          # local | cloud
model = "nllb-200-distilled-600M"
```

Для каждого блока — команда тестирования на реальных данных пользователя
(`scripts/select_model.py --component stt|tts|translation`), пишущая
результат в конфиг:
- **STT** — почти готово: `c0_spike.py` (RTF/RSS) + WER-фикстуры H2
  (критерий 3, `tests/fixtures/acceptance_stt/`) уже делают то же самое,
  нужно только собрать в единый интерфейс подбора модели.
- **TTS** и **перевод** — такого инструмента нет вообще, писать с нуля по
  тому же паттерну (замер скорость/память/качество → вердикт).

### Локальные кандидаты

- **STT** — уже локальный (whisper.cpp), меняется только выбор модели
- **TTS локально** — Piper (лёгкий, CPU-friendly, ~50-200МБ на голос) или
  Coqui/XTTS (тяжелее, лучше качество, обычно требует GPU для приемлемой
  скорости)
- **Перевод локально** — NLLB-200 (дистиллированная ~600M, специализированная
  MT-модель — компактнее и точнее для перевода, чем общая LLM) или
  маленькая квантованная LLM (~3B Q4, ~2ГБ)

**Конфликт со спекой (оба пункта — явные запреты, не пробелы):**
- TTS — `SPEC_speech_local_v2.md`, раздел 14: «TTS и озвучка — Исключено»
  (см. также Tier 1.6 выше)
- NLLB / тяжёлый локальный ML-рантайм — прямо в списке запрещённого в MVP:
  «Ollama, локальная LLM, pyannote, NLLB, ..., тяжёлый Python-ML runtime»

### Бюджетные тиры

- **Минимальный (2-3ГБ):** STT `base/small` локально, TTS/перевод — облако
  или выключено (по сути текущая архитектура)
- **Полностью локальный (5-8ГБ):** STT `small/medium`, TTS Piper, перевод
  NLLB — всё одновременно резидентно, требует научить каскад деградации
  (`app/watchdog/degradation.py`) учитывать память TTS/MT-моделей, а не
  только whisper, как сейчас

### Архитектурное следствие — пересмотр CAPABILITY_MATRIX

Сейчас `Capability.TEXT_TO_CLOUD` разрешён **в обоих** профилях, включая
`confidential`, — альтернативы локальному переводу не было. Как только
появляется локальный перевод, в `confidential` профиле `TEXT_TO_CLOUD`
для перевода должен быть **запрещён**, а не оставлен опцией на выбор:
профиль называется «конфиденциальный», значит в нём перевод обязан идти
только локально, когда локальный вариант доступен. Это правка матрицы
изоляции (задача A6/J4), а не просто добавление конфига.

### Что это НЕ меняет

Открытый вопрос «на какой платформе звонить» (Zoom/Meet/Teams vs
self-hosted Jitsi/Matrix и т.п.) — решение пользователя, ортогональное
этому репозиторию. `speech-local` уже платформо-агностичен (слушает
произвольный узел PipeWire), то есть технически уже совместим с любой
такой платформой без единой правки кода — задача не в коде, а в выборе
инфраструктуры пользователем.
