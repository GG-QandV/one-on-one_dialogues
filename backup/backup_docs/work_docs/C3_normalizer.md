# C3 — нормализатор аудио (резервный путь)

| | |
| :-- | :-- |
| Файл | `app/audio/normalizer.py` |
| Уровень | Middle |
| Оценка | 150 LOC, 8 тестов |
| Зависит от | `app/audio/pcm.py` (готов), `app/audio/capture.py` (готов) |
| Блокирует | STT-конвейер на нестандартном источнике звука |
| Пункт спеки | §7, §6 (формат аудио) |

## Задача

Привести поток к формату, который принимает whisper: **16 кГц, моно,
s16le PCM**. Формат зафиксирован жёстко (`pcm.py`: `SAMPLE_RATE=16000,
CHANNELS=1, SAMPLE_WIDTH=2`); любой код ниже по конвейеру предполагает
его и на другом формате тихо теряет качество.

**Ключевое проектное решение, которое закрывает этот контракт.**
`INTERFACES.md` §2.3 фиксирует отклонение от спеки §7, ожидающее
утверждения владельца: нормализация делается самим `pw-record`
(16 кГц/моно/s16le), FFmpeg — резервный бэкенд, не в горячем пути.
Экономия — один процесс и 40–80 МБ RAM на два потока.

Контракт принимает это отклонение и оформляет normalizer **как резервный
путь, а не как звено горячего конвейера**:

- когда источник — `pw-record` с правильными параметрами, `AudioChunk`
  уже нормализован, и normalizer в цепь **не включается вообще**;
- normalizer вызывается только когда источник отдаёт иной формат:
  резервный захват через FFmpeg-бэкенд, чтение файла на воспроизведении,
  будущий источник тир 2 (браузерное расширение), тестовые WAV с иной
  частотой.

Из этого следует форма модуля: **не поток, а преобразователь буфера**.
Он не встаёт между `capture` и `vad` постоянно; он вызывается точечно там,
где формат не гарантирован.

## Интерфейс

```python
@dataclass(frozen=True, slots=True)
class AudioFormat:
    sample_rate: int
    channels: int
    sample_width: int              # байт на семпл: 2 = s16le

    @property
    def is_target(self) -> bool:   # 16000/1/2
        ...

TARGET = AudioFormat(sample_rate=16000, channels=1, sample_width=2)

@dataclass(frozen=True, slots=True)
class NormalizerConfig:
    ffmpeg_path: str = "ffmpeg"
    timeout_s: float = 10.0
    max_buffer_bytes: int = 32_000_000   # ~16 мин при 16к моно; страховка

class AudioNormalizer:
    def __init__(self, config: NormalizerConfig | None = None,
                 *, runner: Any | None = None) -> None: ...

    def needs_normalization(self, fmt: AudioFormat) -> bool: ...

    async def normalize(self, pcm: bytes, src: AudioFormat) -> bytes: ...
        # -> PCM в формате TARGET; на TARGET-входе возвращает pcm без вызова FFmpeg

    def snapshot(self) -> dict: ...
```

## Поведение

1. **Быстрый путь — без работы.** `needs_normalization(TARGET)` →
   `False`; `normalize(pcm, TARGET)` возвращает `pcm` как есть, **не
   запуская FFmpeg**. Это основной сценарий (`pw-record` уже отдаёт
   нужный формат), и он обязан быть бесплатным: ни процесса, ни копии
   буфера.

2. **Резервный путь — FFmpeg-подпроцесс.** При `src != TARGET` запускается
   FFmpeg с явным выходным форматом: `-ar 16000 -ac 1 -f s16le`. Вход
   передаётся через stdin (`-f <src fmt> -i pipe:0`), выход читается из
   stdout. Аргументы командной строки не содержат данных — только
   параметры формата.

3. **Запуск подпроцесса — по образцу `stt/runner.py` (готов).** Не
   изобретать второй паттерн запуска: тот же `asyncio.create_subprocess_exec`,
   тот же таймаут через `wait_for`, то же убийство процесса при
   превышении. `runner` инъектируется параметром для тестов —
   перехватить вызов без реального FFmpeg.

4. **Таймаут обязателен.** FFmpeg на битом входе виснет. Превышение
   `timeout_s` → процесс убивается, бросается `AudioNormalizationFailed`
   (подкласс из `app/errors.py`) **без** содержимого буфера в сообщении:
   в аудио — переговоры.

5. **Клиппинг при конверсии.** Вход float вне диапазона [-1, 1] при
   свёртке в int16 даёт треск, который whisper ловит как артефакты речи.
   FFmpeg клиппит сам при `-f s16le`; контракт фиксирует, что
   дополнительной нормализации громкости модуль **не делает** — это не
   его задача и меняло бы `raw` сигнал.

6. **Пустой и тихий вход — валидны.** Пустой буфер → пустой буфер, без
   запуска процесса. Поток из тишины → нормализованная тишина. Решение
   «где речь» принимает `vad.py`, не normalizer.

7. **Граница буфера.** `max_buffer_bytes` — страховка от передачи всей
   часовой сессии одним куском: превышение → `AudioNormalizationFailed`
   с кодом `buffer_too_large`. Normalizer работает на фрагментах
   (сегмент, файл), не на всём потоке.

8. **Определение формата не угадывается.** `src: AudioFormat` передаётся
   вызывающим — он знает источник. Модуль не парсит заголовки и не
   пробует определить частоту по содержимому: это ненадёжно и не его
   ответственность.

9. **Функция без состояния между вызовами.** `snapshot()` копит только
   счётчики (сколько прошло быстрым путём, сколько через FFmpeg, отказы) —
   для экрана диагностики E5.

10. **Ни БД, ни сети.** Только подпроцесс FFmpeg.

## Запрещено

- Включать normalizer в горячий путь `capture → vad`, когда источник уже
  отдаёт TARGET: это возвращает те самые 40–80 МБ и процесс, ради
  экономии которых принято отклонение §2.3.
- Запускать FFmpeg на TARGET-входе.
- Запускать FFmpeg без таймаута.
- Передавать аудио аргументом командной строки (видно в `ps`).
- Нормализовать громкость, применять фильтры, шумоподавление: это меняет
  сигнал, а `raw` должен оставаться сырым.
- Делать VAD, отбрасывать тишину.
- Буферизовать весь поток сессии в память.
- Угадывать формат входа по содержимому.
- Логировать содержимое буфера на любом уровне.
- Тянуть аудио-библиотеки (`librosa`, `soundfile`, `pydub`): FFmpeg
  делает всё, лишняя зависимость в MVP не нужна.

## Критерии приёмки

- [ ] `needs_normalization(TARGET)` → `False`
- [ ] `needs_normalization(44100/2/2)` → `True`
- [ ] `normalize(pcm, TARGET)` возвращает тот же объект, FFmpeg не
      запускался (проверяется подменённым `runner`, падающим при вызове)
- [ ] `normalize(pcm, 48000/2/2)` вызывает FFmpeg с `-ar 16000 -ac 1
      -f s16le`, аудио уходит в stdin, в аргументах его нет
- [ ] Зависший FFmpeg убивается по `timeout_s` → `AudioNormalizationFailed`,
      в сообщении нет содержимого буфера
- [ ] Пустой буфер → пустой буфер, процесс не запускался
- [ ] Буфер сверх `max_buffer_bytes` → `AudioNormalizationFailed`
      (`buffer_too_large`)
- [ ] Модуль не импортирует `librosa`/`soundfile`/`pydub`/`sqlite3`/`httpx`
      (проверяется грепом)

## Подсказки

Форма вызова FFmpeg (параметры входа зависят от `src`):

```python
args = [
    cfg.ffmpeg_path,
    "-hide_banner", "-loglevel", "error",
    "-f", src_ffmpeg_fmt, "-ar", str(src.sample_rate),
    "-ac", str(src.channels), "-i", "pipe:0",
    "-ar", "16000", "-ac", "1", "-f", "s16le", "pipe:1",
]
```

Запуск и таймаут — копировать из `stt/runner.py`, а не писать заново:
там уже решены зомби-процессы и убийство по таймауту.

Ловушки:
- `-f s16le` на выходе обязателен: без явного формата FFmpeg по
  расширению `pipe:1` формат не определит и вернёт WAV с заголовком,
  который whisper примет за первые семплы;
- `stderr` в `PIPE` и читать при ошибке (для `snapshot`), но не в лог с
  содержимым; `stdout` — данные, не смешивать с `stderr`;
- проверить, что вызывающий код (`capture` при FFmpeg-бэкенде, чтение
  файла) действительно знает `src`-формат: если он сам его не знает,
  проблема в нём, а не в normalizer;
- быстрый путь (п. 1) — не микрооптимизация: при часовой встрече и потоке
  сегментов лишний запуск FFmpeg на уже готовом формате удвоил бы число
  процессов, что и есть предмет отклонения §2.3.

## Отдельно: утверждение владельца

Отклонение §2.3 (нормализация в `pw-record`, FFmpeg резервный) помечено в
`INTERFACES.md` как «ожидает утверждения владельца». Этот контракт
исходит из того, что отклонение **принято**. Если владелец решит вернуть
нормализацию в горячий путь (FFmpeg всегда), контракт переписывается:
normalizer становится потоковым звеном между `capture` и `vad`, и оценка
LOC/RAM меняется. **До реализации подтвердить у владельца, что отклонение
в силе.**
