# Задание Middle- и Junior-агентам: реализация и механика

Два потока работы. Middle пишет код по готовым контрактам и чинит
дефекты по диагнозу из аудита. Junior делает механические правки без
решений. Оба потока идут параллельно с аудитом Senior — но с оговоркой в
конце.

# ПОТОК MIDDLE

## M1. Реализация модулей по волнам (контракты готовы)

Порядок — строго по волнам зависимостей. Внутри волны задачи
независимы, можно параллелить между агентами.

```
ВОЛНА 1 — доступна сейчас:
  D2  gemini_text.py    контракт D2  [фикстура literal_20 готова]
  D3  claude_text.py    контракт D3  [фикстура literal_20 готова]
  D6  context.py        контракт D6  [нужна миграция 002 — готова]
  I4  translate.py      контракт I4
  G1  redactor.py + logging_setup.py  контракт G1  [test_log_redaction]

ВОЛНА 2 — после волны 1:
  D7  offline.py        контракт D7
  G2  byok.py           контракт G2  [G1 ОБЯЗАТЕЛЬНО принят]
  I1  library.py        контракт I1  [миграция 003 — готова]
  E1  server.py + routes.py  контракт E1

ВОЛНА 3 — после волны 2:
  I2  provider.py       контракт I2  [draft_questions_15 готова]
  F1  memory.py         контракт F1

ВОЛНА 4:
  I3  trigger.py        контракт I3
  C3  normalizer.py     ← ждёт контракт от architect
```

Жёсткие правила (нарушение = переделка):

- **G1 принят полностью до старта G2** — иначе первый живой ключ в логе.
- **D2/D3 сверяются на одной фикстуре** `literal_20.json` — числа, даты,
  имена, URL идентичны входу у обоих провайдеров.
- **Каждый модуль — свои тесты по критериям приёмки контракта**, до
  открытия PR.

Процесс на каждый файл — стандартный:

1. Прочитать контракт целиком, включая «Подсказки».
2. Выписать чекбоксы «Критериев приёмки» — это список тестов.
3. Тесты до кода.
4. Код.
5. `ruff` + `mypy --strict` + `pytest`.
6. Пройти «Запрещено» построчно.
7. PR: закрытые чекбоксы, незакрытые с причиной.

## M2. Реализация вкладок UI (после контрактов от architect)

Когда architect выдаст `E4/E5/E6/E7/E8`, реализовать по образцу
`tab_translation.js` (E3, готов). **Главный инвариант, общий для всех:**
вкладка не ведёт своего состояния, подписывается через `stream.subscribe`,
читает `stream.getState()`, рисует дельту. Это тот инвариант, нарушение
которого развело E3 с E2 — не повторять.

Порядок реализации вкладок (по приоритету для живого теста):
`topbar` → `settings` → `tab_diagnostics` → `tab_drafts` → `history`.

## M3. Исправление дефектов из аудита (после отчёта Senior)

Когда `docs/AUDIT_partII.md` готов — каждый пункт со статусом `ДЕФЕКТ`
становится задачей. Правило: **чинить строго по диагнозу, не расширяя
область.** Диагноз содержит файл, строку, пункт спеки и что именно не так.
Задача — привести код к спеке, а не «улучшить попутно».

BLOCKER-дефекты (из раздела A аудита) — вперёд волн реализации: их
нарушение валит приёмку §21, и чинить их важнее, чем писать новые модули.

## M4. Сквозная сборка main.py (H1) — Senior или сильный Middle

Отдельная задача после волн 1–2: соединить конвейер целиком и прогнать
живой поток от `capture` до карточки. В роадмапе H1 — «первая полная
сборка, устранение дрейфа интерфейсов», вероятность срыва 40%. Это не
кодинг нового, а стыковка готового: порознь собранные модули почти
никогда не складываются с первого раза. Отдельный PR, отдельная сессия.

# Оговорка про параллельность (важно для всех трёх потоков)

Потоки идут одновременно, но с одной точкой синхронизации:

- **Junior J1/J2/J3** — можно прямо сейчас, ни от чего не зависят.
- **Senior аудит** — прямо сейчас, read-only, никому не мешает.
- **Middle волна 1** — прямо сейчас, контракты готовы.
- **Middle M3 (починка дефектов)** — только ПОСЛЕ отчёта аудита.
- **Middle M2 (вкладки)** — только ПОСЛЕ контрактов от architect.

Конфликт возможен в одном месте: если аудит найдёт BLOCKER в модуле, для
которого Middle уже пишет зависимый код (например, дефект в `privacy.py`,
на который опирается D2). Правило: **BLOCKER из аудита останавливает
зависимые задачи волны до исправления.** Поэтому раздел A аудита делается
первым — чтобы блокеры всплыли раньше, чем на них навяжут новый код.
