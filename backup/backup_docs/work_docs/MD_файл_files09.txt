Решения, принятые в этих шести

Где	Решение	Обоснование
G2	TTL отсчитывается от put, использование его не продлевает	Иначе активная сессия держит ключ бесконечно, и «60 минут» из §16 перестаёт что-либо означать
G2	В docstring и README фиксируется, что затереть ключ в памяти Python нельзя	§16 прямо требует честной формулировки вместо обещания недоступности
G3	Текст только через stdin	Аргументы командной строки видны в ps любому процессу пользователя
G4	Сегмент нулевой длительности в SRT/VTT растягивается до 1000 мс, в JSON — как в БД	Плеер ломается на нулевой длительности; JSON — audit-след, править его нельзя
E1	SSE, а не WebSocket; при reconnect — снапшот, не переигрывание истории	Поток односторонний; хранение истории событий на сервере — второй источник правды рядом с БД
E2	Состояние и логика вытеснения — в клиентском слое потока, не в отрисовке	Иначе каждая вкладка UI получит свою версию вытеснения fast → accurate
E3	Черновик и проверенный перевод никогда не показываются одновременно	Человек читает вслух с экрана; спутанный черновик = озвученная клиенту неверная сумма

Ограничения выполнения

E2 и E3 — фронтенд; в загруженном INTERFACES.md для них зафиксирован только контракт событий (§7.1) и строка «дедупликация по (тип, id, sequence)». Имена файлов (stream.js, cards.js) и API модулей предложены мной — в INTERFACES.md их нет, при расхождении с вашей структурой правьте пути в шапке контрактов.
Порог «сироты» быстрого трека в 30 секунд (E2 п. 5, E3 п. 8) в спеке отсутствует — значение выбрано мной, вынесено в конфиг не было. Стоит добавить в [ui] при следующей правке config.toml.
G4 покрывает четыре формата, которые в роадмапе разнесены на G4 и G5 — я собрал их одним контрактом, поскольку они делят таймкод-хелперы и один источник данных. Если нужна разбивка под двух разных агентов, скажите — разделю на G4 (TXT/JSON) и G5 (SRT/VTT).
