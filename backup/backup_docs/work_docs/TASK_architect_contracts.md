# Задание Architect-агенту: недостающие контракты

Два пробела, где кода нет и контракта нет. Здесь нужно **проектирование
интерфейса**, а не кодинг — поэтому architect, а не middle. Результат
каждой задачи — файл-контракт по образцу существующих в `CONTRACTS/`
(структура: шапка-таблица, Задача, Интерфейс, Поведение, Запрещено,
Критерии приёмки, Подсказки).

Образец плотности — `CONTRACTS/D4_prompts.md` и `CONTRACTS/G1_log_redactor.md`:
раздел «Запрещено» пишется по конкретным ошибкам, «Подсказки» содержат
ловушки, экономящие итерацию.

## Задача 1 — `CONTRACTS/C3_normalizer.md`

Модуль `app/audio/normalizer.py` (пуст) — вход всего STT-конвейера.
`capture.py` (готов) отдаёт сырой поток, `normalizer` приводит его к
формату, который принимает whisper: **16 kHz, mono, s16le PCM**.

Что должен решить контракт (проектные вопросы, ответь в нём):

1. **Транспорт нормализации.** FFmpeg-подпроцесс (как заявлено в дереве:
   «C3: FFmpeg → 16k mono s16le») или библиотека? Дерево говорит FFmpeg —
   значит подпроцесс, и тогда те же правила, что у C4/runner: таймаут,
   инъекция для тестов, никакого зомби-процесса. Свериться с тем, как
   `runner.py` (готов) запускает whisper-cli — использовать тот же
   паттерн запуска подпроцесса, а не изобретать второй.

2. **Потоковость.** Нормализация идёт непрерывным потоком (капля за
   каплей от `capture`) или пофрагментно (по сегменту от сегментера)?
   Это определяет, где normalizer в конвейере: до VAD (нормализует
   поток) или после сегментера (нормализует нарезанные куски). Прочитать
   `INTERFACES.md` и `capture.py`/`pcm.py`/`segmenter.py`, чтобы понять
   фактическое место врезки. **Это ключевое решение контракта** — от него
   зависит сигнатура.

3. **Ресемплинг и клиппинг.** Вход может быть 44.1/48 kHz стерео float.
   Понижение частоты, свёртка в моно, конверсия в s16le — что делает
   FFmpeg сам, что проверять на выходе. Клиппинг при конверсии float→int16
   — ловушка: значения вне [-1,1] дают треск, whisper ловит его как
   артефакты речи.

4. **Тишина и пустой вход.** Пустой буфер, поток из одной тишины — не
   ошибка, а валидный выход (whisper на тишине вернёт пустой Transcript,
   C6 это уже умеет). Контракт фиксирует: normalizer не решает, где речь —
   это VAD.

Обязательные разделы «Запрещено» — минимум:
- не менять частоту/каналы иначе, чем в 16k/mono/s16le (whisper обучен
  на этом, другой формат тихо роняет качество);
- не запускать FFmpeg без таймаута;
- не буферизовать весь поток в память (часовая встреча = гигабайты);
- не делать VAD, не отбрасывать «тихие» куски — это ответственность
  `vad.py`.

Оценка: middle-уровень реализации, ~150 LOC, 8 тестов (по образцу
соседних C-контрактов).

## Задача 2 — контракты на 5 пустых вкладок UI

Пять `.js`-файлов пусты, контрактов на них нет вообще. Без них живой тест
проверяет только вкладку перевода. Нужны контракты; писать их по образцу
E3 (`tab_translation.js` уже готов и служит эталоном интеграции с E2).

**Общий инвариант для всех пяти** (из E2/E3, повторить в каждом
контракте): вкладка **не ведёт своего состояния и не разбирает события
сама** — подписывается на `stream.subscribe`, читает `stream.getState()`,
рисует. Логика — в E2. Это тот самый инвариант, нарушение которого уже
один раз развело E3 с E2; каждый новый контракт обязан его зафиксировать
в «Запрещено».

| Файл | Контракт | Вкладка §14 | Что показывает | Приоритет для живого теста |
| :-- | :-- | :-- | :-- | :-- |
| `topbar.js` | `E6_topbar.md` | Верхняя панель | Профиль (переключатель), индикатор языка + конфликт (C8), статус провайдера, состояние соединения | **Высокий** — без переключения профиля живой тест не проверяет §21.7 |
| `tab_drafts.js` | `E4_tab_drafts.md` | Вкладка «Черновики» | Черновики: `draft_ru`, перевод, источники, `has_gaps`, кнопка «Копировать» (G3) | **Средний** — нужен для сценария черновиков, не для ядра |
| `tab_diagnostics.js` | `E5_tab_diagnostics.md` | Вкладка «Диагностика» | `snapshot()` от memory (F1), offline (D7), byok TTL (G2), уровни аудио, задержки | **Средний** — критичен для отладки живого теста, но не для самого прогона |
| `settings.js` | `E7_settings.md` | Панель настроек | Ввод ключа (BYOK), выбор провайдера, языки потоков, библиотека фактов (I1), пороги | **Высокий** — без ввода ключа и раздела библиотеки нечего тестировать |
| `history.js` | `E8_history.md` | История сессий | Список прошлых сессий, экспорт (G4), повтор перевода сегмента | **Низкий** — постфактум, для живого теста не нужен |

**Проектные вопросы, общие для всех пяти:**
- каждая вкладка — отдельный модуль с `mount()`/`unmount()` по образцу
  E3, или общий контейнер с переключением? Прочитать `stream.js` и
  `tab_translation.js`, понять фактическую схему монтирования;
- команды (ввод ключа, переключение профиля, старт/стоп) идут POST-ами на
  E1 (`server.py`, пуст) — значит контракты вкладок зависят от контракта
  E1 и от роутов `routes.py` (пуст). Зафиксировать зависимость, возможно
  сначала нужен контракт на `routes.py`;
- `settings.js` касается ключа BYOK — повторить запрет G2: ключ не
  логируется, не кладётся в DOM-атрибуты, маскируется при отображении.

**Порядок выдачи контрактов:** сначала `E6_topbar` и `E7_settings`
(высокий приоритет — без них живой тест ядра неполон), затем
`E5_diagnostics` (нужен для отладки прогона), затем `E4_drafts`, в конце
`E8_history`.

## Границы

- Контракты, не код. Реализацию отдадут middle-агентам.
- Не проектировать вкладки в отрыве от E1/routes: если серверных роутов
  для команды вкладки нет — это зависимость, зафиксировать, а не
  придумывать протокол на ходу.
- Не дублировать логику состояния в контрактах вкладок — она в E2, каждый
  контракт лишь ссылается.
- Проектные решения C3 (место врезки, транспорт) обосновать чтением
  готового кода конвейера, а не выбрать наугад: сигнатура, не совпавшая
  с тем, что отдаёт `capture`, сломает сборку H1.
