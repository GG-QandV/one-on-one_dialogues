# ROADMAP / WORKFLOW: speech-local MVP

Статус документа: рабочий, используется наравне со спекой (`SPEC_speech_local_MVP.md`) и архитектурой проекта.
Метрика планирования: **задачи, LOC, итерации ревью, вероятности** — не дни и не часы.

---

## 0. Как читать этот документ (для всех моделей-участников)

| Колонка | Смысл |
| :-- | :-- |
| ID | Идентификатор задачи, используется в коммитах, ревью и отчётах |
| LOC | Оценка объёма кода, разброс ±15% (достоверность оценки 85%) |
| Ур. | Требуемый уровень исполнителя |
| P1 | Вероятность, что реализация пройдёт оба ревью с первого раза |
| Итер. | Ожидаемое число циклов «правка → ревью», следует из P1 |
| Тесты | Количество тестов на задачу / ожидаемое число правок тестов |
| Блок. | Что задача блокирует |

**Формула итераций:** ожидаемое число циклов ≈ 1/P1, округление вверх. При P1 ≤ 45% задача обязана дробиться на подзадачи до передачи агенту.

**Достоверность прогнозов документа:**
- LOC — 85%
- P1 (корректность с первого прохода) — 60–70%
- Количество тестов — 75%
- Вероятности архитектурных срывов (раздел 2) — 55–65%, зависят от ответов на раздел 3

## 1. Роли и конвейер ревью

### 1.1 Исполнители

| Уровень | Модели | Что берут |
| :-- | :-- | :-- |
| Junior | DeepSeek Flash, Haiku 4.5 | Изолированные модули с готовым контрактом и падающим тестом |
| Middle | DeepSeek Pro, Sonnet 4.6 | Модули с внешними зависимостями (HTTP, SSE, парсинг) |
| Senior | Opus 4.8, Opus 5 | Сквозная логика, конкурентность, процесс-менеджмент, состояние |
| Архитектор | Opus 5, Fable 5 | Контракты, интерфейсы, каскад деградации, дробление задач |

### 1.2 Ревьюеры

| Ревьюер | Зона ответственности | Право вето |
| :-- | :-- | :-- |
| **Владелец проекта (человек)** | Корректность архитектуры, соответствие функционала цели, качество выбора и настроек моделей в процессе, приёмка результата | Да, финальное |
| **ChatGPT 5.6** | Соответствие спеки архитектуре; соответствие кода спеке и архитектуре; выявление расхождений и недоговорённостей | Да, на уровне задачи |
| Senior-агент | Технический ревью кода Junior/Middle до внешнего ревью | Нет, возвратный |

### 1.3 Конвейер задачи

```
Архитектор: контракт + падающий тест
  -> Исполнитель: реализация
  -> Senior-агент: технический ревью (если исполнитель Junior/Middle)
  -> ChatGPT 5.6: соответствие спеке/архитектуре
  -> Владелец: архитектура, функционал, качество
  -> DONE или возврат на итерацию с указанием пункта спеки
```

**Правило возврата:** возврат всегда содержит ссылку на пункт спеки или контракта, который нарушен. Возврат без ссылки не принимается — это признак того, что требование отсутствует в спеке и его нужно сначала внести.

## 2. Архитектурные риски: вероятности срыва

Оценка вероятности того, что архитектура потребует пересмотра **в процессе реализации** (не косметической правки, а изменения решения).

| # | Риск | Вероятность | Что ломает | Триггер обнаружения |
| :-- | :-- | --: | :-- | :-- |
| R1 | CPU не тянет live: обработка 10 с фрагмента > 10 с | **50–60%** | Весь live-режим; переход в recording+post-processing | Блок C, задача C4 |
| R2 | Противоречие «два потока» ↔ «не более одного экземпляра whisper.cpp» | **75–85%** | Двусторонний режим невозможен в заявленном виде; нужен мультиплексор или пересмотр запрета | Блок C, задача C5 |
| R3 | Смешение двух парадигм whisper: `stream` (скользящее окно) vs файл-на-сегмент | **60–70%** | Схема `segments` с `local_audio_path` и VAD-границами не стыкуется со streaming-режимом | Блок A, при написании контракта C |
| R4 | Реальный RSS процесса выше «388 МБ модели»: буферы, KV-состояние, аудиоочередь | **45–55%** | Бюджет 1.3–1.6 ГБ; пороги watchdog | Блок F, задача F1 |
| R5 | Захват системного звука без ручного virtual sink недостижим | **60–70%** | Не ломает — спека это уже допускает; ломает только ожидания демо | Блок C, задача C1 |
| R6 | `avg_logprob` недоступен в выбранном режиме вывода whisper.cpp | **35–45%** | Поле `stt_confidence`; деградация до NULL | Блок C, задача C6 |
| R7 | Суммарная задержка live: VAD 0.6 с + STT + облачный API 1–3 с = 3–6 с | **40–50%** | Понятие «live captions»; возможен отказ от режима на длинных сегментах | Блок D, задача D2 |
| R8 | Встроенный VAD whisper.cpp даёт границы хуже требуемых 1.5–8 с | **40–50%** | Качество сегментации; возможен отдельный VAD | Блок C, задача C5 |
| R9 | Дрейф интерфейсов между параллельными агентами | **50–60%** | Интеграция блоков D, E, F | Первая интеграционная сборка |
| R10 | Агент отдаёт заглушку под видом реализации | **70–80%** (хотя бы один случай) | Достоверность отчётов о готовности | CI-проверка + ревью |

### Сводные вероятности

| Событие | Вероятность |
| :-- | --: |
| Архитектура пройдёт реализацию без единого пересмотра решений | **10–15%** |
| Потребуется 1–2 существенных пересмотра | **45–55%** |
| Потребуется 3+ пересмотра (кандидат на переработку спеки) | **30–40%** |

**Главный вывод:** R2 и R3 — не риски, а **дефекты спеки, уже присутствующие в тексте**. Они обнаружены до начала кода и должны быть закрыты в блоке A, иначе блок C гарантированно уйдёт в 3+ итерации.

**Ожидаемый суммарный объём переписанного кода за итерации:** при среднем P1 = 62% и средней глубине 2.1 итерации фактический объём написанного кода превысит финальный в **1.6–1.9 раза** (достоверность 60%) — то есть 17 000–20 000 LOC суммарной генерации при финальных ~10 800.

## 13. Правила для агентов-исполнителей

1. **Задание = контракт + падающий тест.** Задача без обоих артефактов не берётся в работу; вместо кода возвращается запрос к Архитектору.
2. **Запрет заглушек.** `pass`, `TODO`, `return None`, `assert True` в местах реальной логики — автоматический возврат по CI (задача A6). Если реализовать невозможно — вернуть отказ с причиной, не имитацию.
3. **Запрет расширения области.** Правки за пределами файлов своей задачи запрещены. Нужна правка чужого модуля — заявка Архитектору.
4. **Ссылка на спеку.** Каждое нетривиальное решение в коде сопровождается ссылкой на пункт спеки. Решение без пункта = кандидат на пробел в спеке, эскалируется.
5. **Один контекст — одна задача.** Задача, не помещающаяся в контекст вместе с контрактом и тестом, возвращается Архитектору на дробление.
6. **Честный отчёт.** Формулировки «полностью выполнено», «соответствует спеке» допустимы только при 100% прохождении контракт-тестов. При частичном выполнении — явный список невыполненного.
7. **Конфиг вместо хардкода.** Любая константа, влияющая на поведение, идёт в `config.toml` (раздел 14a спеки).

## 15. Что считается провалом этапа

- Отчёт о готовности при непройденных контракт-тестах.
- Реализация, обходящая инвариант неизменяемости `raw_text`.
- Появление ключа BYOK в БД, файле, URL или логе.
- Передача аудио или локальных путей во внешний API.
- Молчаливое изменение архитектурного решения исполнителем без эскалации.
- Тест, подогнанный под реализацию вместо реализации под контракт.
