# H6 — стенд приёмки MVP: 16 критериев спеки §21

| | |
| :-- | :-- |
| Файл | `tests/acceptance/` (пакет), `scripts/acceptance.py` |
| Уровень | Senior |
| Оценка | 450 LOC, 16 проверок (11 автоматических, 5 с участием человека) |
| Зависит от | **все модули блоков B–I**, H1 (первая полная сборка) |
| Блокирует | закрытие MVP |
| Пункт спеки | §21 (критерии 1–16), §17 (обязательные тесты) |

## Задача

Превратить 16 критериев §21 из списка в исполняемый прогон: один вход,
одна таблица результатов, воспроизводимость на чистой машине.

Модульные тесты каждого контракта проверяют модуль. Здесь проверяется
**система**: что сегмент доходит от микрофона до экспорта, что
переключение профиля действительно обрывает аудио-канал, что ключ
действительно отсутствует в логах. Ни одна из этих проверок не
принадлежит отдельному модулю, и потому без общего стенда они не
делаются никогда.

Часть критериев проверяется только на живом железе (§21.1, 2, 5, 6) —
их автоматизировать нельзя, но можно свести к скрипту с замерами и
чек-листу, где человек нажимает и подтверждает.

## Интерфейс

```python
class CheckKind(str, Enum):
    AUTO = "auto"                 # прогоняется в CI/локально без человека
    LIVE = "live"                 # требует живого железа и участия человека

@dataclass(frozen=True, slots=True)
class CheckResult:
    number: int                   # номер критерия §21
    title: str
    kind: CheckKind
    passed: bool | None           # None = не выполнялся
    detail: str                   # измеренное значение или причина провала
    evidence_path: Path | None    # лог, дамп трафика, экспорт

async def run_all(*, include_live: bool = False) -> list[CheckResult]
def report_markdown(results: list[CheckResult]) -> str
```

Запуск: `python scripts/acceptance.py [--live] [--only 5,7,15]`.

## Карта критериев

| № §21 | Критерий | Вид | Способ проверки |
| --: | :-- | :-- | :-- |
| 1 | Запуск без Docker/GPU/тяжёлого ML | LIVE | Установка на чистую Mint, скрипты B7, фиксация версий |
| 2 | Раздельный захват узла и микрофона одновременно | LIVE | `diagnose()` обоих потоков, ненулевой RMS в обоих |
| 3 | Распознавание EN/ES/RU/UA/PL через `ggml-base.bin` | AUTO | 5 эталонных WAV, сверка с ожидаемым текстом по WER-порогу |
| 4 | `raw_text` + таймкоды + `stt_confidence` в SQLite, только от whisper | AUTO | Прогон фикстуры, проверка полей; попытка `UPDATE raw_text` → ошибка |
| 5 | Задержка точного трека ≤ 3000 мс, медиана по 50 репликам | LIVE | Замер `t_end_ms` → появление перевода, гистограмма |
| 6 | Черновик быстрого трека ≤ 1500 мс, замещается проверенным | LIVE | Замер по событиям SSE, проверка `superseded_ids` |
| 7 | Переключение профиля рвёт аудио-сессию; в конфиденциальном профиле аудио-трафика нет | AUTO | Перехват транспорта + счётчик байтов, `switch()` посреди сессии |
| 8 | `privacy_profile` проставлен у каждого сегмента | AUTO | `SELECT COUNT(*) WHERE privacy_profile IS NULL` = 0 |
| 9 | `live_literal` не меняет числа, даты, имена, URL (20 фрагментов) | AUTO | `tests/fixtures/literal_20.json`, оба провайдера |
| 10 | Черновик генерируется на вопрос, содержит источники, `has_gaps` при нехватке | AUTO | Библиотека-фикстура, вопрос с фактом и вопрос без факта |
| 11 | Черновик недоставим без действия пользователя; горячая клавиша работает | AUTO + LIVE | Граф вызовов: нет пути `generate → copy`; клавиша — вручную |
| 12 | Облако недоступно → запись и STT продолжаются, очередь догоняется | AUTO | Транспорт отвечает 503, затем 200; сверка числа сегментов |
| 13 | Экспорт содержит только точный трек | AUTO | Строка `track='fast'` в БД → отсутствует во всех форматах |
| 14 | Memory pressure: очередь на диск, `MemoryMax` не превышен аварийно | AUTO | Подменённый `MemoryReader`, проверка действий каскада |
| 15 | Ключ BYOK не на диске и не в логах | AUTO | Канареечный ключ + грep по логам, БД, temp, дампам |
| 16 | Остановка и перезапуск не повреждают сессию, задачи восстанавливаются | AUTO | Убийство процесса `SIGKILL`, старт, `recover()` |

## Поведение

1. **Каждая проверка независима.** Своя временная директория, своя БД,
   свой конфиг. Провал одной не мешает остальным: прогон обязан дойти до
   конца и показать полную картину, а не первую ошибку.

2. **Ни одного обращения к настоящим облачным провайдерам** в режиме
   AUTO. Транспорт подменяется; ответы — из фикстур. Критерий 9 в
   AUTO-режиме проверяет разбор и сохранность сущностей на записанных
   ответах; проверка на живых моделях — задача H2 (владелец).

3. **Критерий 7 — перехват на уровне транспорта, а не доверие коду.**
   Считаются фактически отправленные байты. Проверка формулируется как
   «после `switch()` в конфиденциальный профиль в сокет аудио-сессии не
   ушло ни одного байта, сессия закрыта», а не «метод `close` был
   вызван».

4. **Критерий 15 — грep по артефактам, а не по коду.** Канареечный ключ
   `sk-CANARY-12345` кладётся в `KeyStore`, прогоняется полный цикл с
   ошибками провайдера (чтобы сработали трейсы), затем поиск строки во
   **всех** файлах, созданных процессом: лог, БД, WAL, temp, экспорт,
   дампы состояния очереди. Найдено хоть где-то — критерий провален.

5. **Критерий 4 проверяет неизменяемость, а не только запись.** Прямой
   `UPDATE segments SET raw_text=...` обязан завершиться ошибкой
   (`ImmutableFieldError` или ошибка триггера БД). Проверка «поле
   заполнено» без проверки «поле нельзя изменить» бессмысленна.

6. **LIVE-проверки не имитируются.** Скрипт готовит окружение, выводит
   инструкцию человеку, ждёт подтверждения и записывает измеренное
   значение. Автоматический «проход» LIVE-критерия без участия
   человека — фальсификация приёмки; при `include_live=False` результат
   `passed=None`, а не `True`.

7. **Отчёт — таблица Markdown** с номером критерия, вердиктом,
   измеренным значением и путём к артефакту. Итоговая строка: пройдено /
   провалено / не выполнялось. Файл отчёта датируется и не
   перезаписывается.

8. **Пороговые критерии печатают число, а не галочку.** «Задержка ≤ 3000
   мс» без указания медианы 2870 мс бесполезна: через месяц никто не
   вспомнит запас.

9. **Прогон идемпотентен.** Повторный запуск на той же машине даёт тот же
   результат; временные директории чистятся, кроме артефактов
   проваленных проверок.

10. **Ошибка внутри проверки — это провал проверки, а не падение
    прогона.** Исключение перехватывается, текст уходит в `detail`.

## Запрещено

- Помечать LIVE-критерий пройденным без участия человека.
- Ходить к настоящим провайдерам в режиме AUTO.
- Проверять критерий 7 по вызовам методов вместо фактического трафика.
- Ограничивать грep по критерию 15 файлом лога: ключ утекает через
  трейсы, дампы и WAL чаще, чем через штатное логирование.
- Переиспользовать одну БД между проверками.
- Останавливать прогон на первом провале.
- Подгонять пороги под фактический результат: 3000 мс и 1500 мс — из
  спеки §21, менять их можно только правкой спеки.
- Считать критерий пройденным при `passed=None`.

## Критерии приёмки самого стенда

- [ ] `run_all()` возвращает ровно 16 результатов, номера 1–16
- [ ] Прогон доходит до конца при провале любой одной проверки
- [ ] `include_live=False` → LIVE-критерии имеют `passed=None`, в отчёте
      отдельная строка «не выполнялось»
- [ ] Отчёт содержит измеренные значения для критериев 5, 6, 14
- [ ] Каждая проверка использует свою временную директорию и свою БД
- [ ] Ни одна AUTO-проверка не открывает сетевого соединения
      (проверяется подменённым сокетом, падающим при вызове)
- [ ] Критерий 15 находит канареечный ключ, если его намеренно записать
      в лог (негативный тест самого стенда)
- [ ] Критерий 13 находит нарушение, если строку `track='fast'` намеренно
      пропустить в экспорт (негативный тест)
- [ ] Критерий 4 находит нарушение, если триггер неизменяемости отключён
      (негативный тест)
- [ ] Исключение внутри проверки даёт `passed=False` с текстом в
      `detail`, прогон продолжается
- [ ] Артефакты проваленных проверок сохраняются, успешных — чистятся
- [ ] `--only 7,15` прогоняет ровно две проверки

## Подсказки

Негативные тесты стенда — не формальность. Стенд, который не умеет
провалить проверку, показывает 16 галочек на пустом месте; три
негативных теста (критерии 4, 13, 15) ловят именно это.

Структура пакета:

```
tests/acceptance/
  conftest.py          # фикстуры окружения, канареечный ключ
  criterion_03_stt.py
  criterion_04_raw_text.py
  criterion_07_privacy.py
  ...
  harness.py           # run_all, report_markdown
scripts/acceptance.py  # CLI-обёртка
```

Ловушки:
- SQLite в режиме WAL держит данные в `-wal`-файле до checkpoint: грep по
  критерию 15 обязан включать `*.db-wal` и `*.db-shm`, иначе ключ
  «не найден» до первого checkpoint;
- критерий 16 требует именно `SIGKILL`, а не `stop()`: корректное
  завершение проверяет другой путь и восстановление очереди не нагружает;
- эталонные WAV для критерия 3 хранить в репозитории (несколько секунд
  каждый) — ссылка на внешний источник делает приёмку невоспроизводимой;
- критерий 5 меряет задержку от **конца произнесения** (`t_end_ms`) до
  появления перевода, а не от начала сегмента: иначе длинные реплики
  «проваливают» порог по определению;
- порог WER для критерия 3 подобрать по фактическому качеству
  `ggml-base.bin` на записанных фрагментах и зафиксировать в фикстуре;
  спека числа не задаёт, и подгонять его после каждого прогона нельзя.
